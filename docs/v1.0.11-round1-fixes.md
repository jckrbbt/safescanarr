VERDICT: FIX-FIRST

The implementation is not safe to ship. I reproduced multiple ways for a previously valid cookie to regain or retain authenticated access after reset, credential changes, epoch revocation, logout, and database restore. The basic cryptography is not the failure: an attacker who lacks app.secret_key could not forge a Flask cookie or the av value in my probes. The failures are state-transition, persistence, and race bugs around otherwise correctly signed cookies.

Concrete issues

1. CRITICAL — Any concurrent config save can roll session_epoch backward and resurrect revoked cookies.

Code evidence:
- web/server.py:965-967 performs read/modify/write as config_module.raw(); existing.update(clean); config_module.save(existing).
- web/auth.py:264-273 independently performs another read/modify/write to bump session_epoch.
- config.py:181-200 atomically replaces the file, but provides no compare-and-swap, process lock, or monotonic merge. Atomic replacement prevents torn JSON; it does not prevent lost updates.

Exact reproduction:
- Probe test_06_config_save_overwrites_epoch starts an authenticated POST /api/config after it has read epoch 0, pauses its save, runs POST /api/auth/revoke-sessions to persist epoch 1, verifies the old cookie now gets 401, then releases the stale config save.
- Output: EVIDENCE CONFIG_SAVE_EPOCH_ROLLBACK {"config_save": 200, "epoch_after": 0, "epoch_before": 1, "operator": 401, "replay_after_save": 200, "replay_before_save": 401, "revoke": 200}
- The stale cookie changed from 401 back to 200. The caller the endpoint promised to keep alive instead became 401 because it had av for epoch 1 while disk reverted to epoch 0.

Impact:
- Revocation is reversible under normal concurrent use. This affects all sessions, not just remembered rows.
- The API’s defence-in-depth removal of session_epoch from submitted JSON at web/server.py:956-959 does not help; the rollback comes from the stale server-side config snapshot.

2. CRITICAL — A later global/CLI revocation can be defeated by an earlier in-flight “sign out other devices” request.

Code evidence:
- web/server.py:523-534 bumps the epoch, does database work, then recomputes and writes the caller’s av from whatever epoch is current at that later instant.
- auth._LOCK is process-local (web/auth.py:34), so it cannot serialize the web process with python -m web.authtool.

Exact reproduction:
- Probe test_16 pauses the web endpoint after its epoch bump, runs python -m web.authtool revoke-sessions in a separate process (epoch becomes 2), then allows the earlier endpoint to finish.
- Output: EVIDENCE INFLIGHT_REVOKE_LAUNDERS_EPOCH {"cli_exit": 0, "epoch_after_cli": 2, "inflight_request": 200, "surviving_session": 200}
- The CLI claimed all sessions were signed out, but the in-flight browser survived with a freshly written epoch-2 av.

Impact:
- “revoke everything, including the device you run it from” is not a reliable security boundary.
- Similar cross-process lost-update risks exist because all auth/config writes use uncoordinated JSON read/modify/write operations.

3. HIGH — Reset + setup does not invalidate a remembered token session when the same token is reused; token A→B→A also resurrects old sessions.

Code evidence:
- web/auth.py:233-236 reset() clears credentials but never bumps session_epoch.
- web/auth.py:200-205 configure_token() saves the token but never bumps session_epoch.
- web/auth.py:246-261 fingerprints only method, credential, and epoch. Returning to the same tuple necessarily returns the same av.
- Remembered web_sessions rows are not removed during reset or credential change.

Exact reproductions:
- Probe test_03: login remembered with token A; auth.reset(); POST /setup with the same token A; replay old cookie.
  Output: EVIDENCE RESET_SAME_TOKEN_RESURRECTION {"epoch": 0, "old_remembered_cookie": 200, "setup": 200}
- Probe test_04: login with token A; configure token B; old cookie gets 401; configure token A again; same old cookie gets 200.
  Output: EVIDENCE CREDENTIAL_ROLLBACK_RESURRECTION {"different_token": 401, "original_token_reused": 200}

Spec violation:
- Design summary line 7 and B documentation promise reset+setup and credential change kill every session. Test case 10 uses password mode; a freshly salted password hash accidentally hides the token-reuse failure.

4. HIGH — Login verification and session establishment are not atomic; an old credential can mint a session bound to the new credential.

Code evidence:
- web/server.py:499-513 verifies first, then calls _establish_session().
- _establish_session at web/server.py:332-347 computes av later from current auth state.
- No lock or generation check spans verify(secret) through av creation.

Exact reproduction:
- Probe test_07 pauses a successful token verification, changes auth to a password, then resumes the old-token login.
- Output: EVIDENCE LOGIN_CREDENTIAL_CHANGE_RACE {"method": "password", "old_secret_accepted_after_change": 200, "resulting_session": 200}
- auth.verify(old_token) is false after the change, but the login response is 200 and the resulting session gets /api/stats 200 because it was stamped with the new password fingerprint.

Impact:
- A credential explicitly rotated away can still authenticate if its request was in flight at the transition.

5. HIGH — Restore publishes untrusted/revoked web_sessions before cleanup; cleanup failure returns success and permanently resurrects cookies.

Code evidence:
- web/server.py:1123-1127 replaces the live DB file first.
- web/server.py:1135 reopens that now-live restored DB.
- Only afterward, lines 1139-1146 attempt to delete restored web_sessions. All exceptions are swallowed.
- Line 1147 returns {status: ok} regardless of reconciliation failure.

Exact reproductions:
- Normal control, probe test_09: revoked cookie stays 401 after a successful restore cleanup.
- Failure, probe test_10: injected real SQLite write failure in delete_web_sessions_except after replacement.
  Output: EVIDENCE RESTORE_FAILURE_RESURRECTION {"before": 401, "old_logged_out_cookie": 200, "restore": 200}
- Race, probe test_11: pause cleanup after the restored file is live and replay the revoked cookie from another client.
  Output: EVIDENCE RESTORE_PUBLICATION_RACE {"after": 401, "before": 401, "during_cleanup_gap": 200, "restore": 200}

Impact:
- A logged-out/stolen remembered cookie can regain full access, including state-changing access using its embedded CSRF token, either permanently on cleanup failure or during the publication gap.
- CHANGELOG.md:15 claims restoring a backup no longer revives remembered devices. That claim is false under both tested conditions.

6. HIGH — SS_TOKEN mode fails open to epoch 0 when config cannot be read, resurrecting pre-bump cookies.

Code evidence:
- web/auth.py:73-87 treats SS_TOKEN as configured even when config_module.raw() fails and explicitly substitutes epoch 0 for every exception.
- session_fingerprint then emits a valid fingerprint for token + epoch 0 rather than returning empty/failing closed.

Exact reproduction:
- Probe test_05 logs in under SS_TOKEN at epoch 0, bumps epoch to 1 (old cookie gets 401), corrupts config JSON temporarily, then replays the old cookie.
- Output: EVIDENCE SS_TOKEN_CONFIG_FAILURE_RESURRECTION {"after_epoch_bump": 401, "config_recovered": 401, "config_unreadable": 200}

Spec problem:
- A2 explicitly prescribed fallback epoch 0. That requirement is itself unsafe. It contradicts the stated fail-closed objective and must be changed, not merely implemented literally.

7. MEDIUM — Logout reports success and clears only the browser copy when server-side deletion fails; a captured cookie remains reusable.

Code evidence:
- web/server.py:380-388 catches delete errors, logs, clears the session, and does not propagate failure.
- /logout at lines 516-519 always returns 200.

Exact reproduction:
- Probe test_08 installs a SQLite trigger that raises on DELETE, calls /logout, removes the fault, and replays the cookie.
- Output: EVIDENCE LOGOUT_FAIL_OPEN {"cookie_replay_after_storage_recovers": 200, "logout": 200}

Impact:
- The UI tells the user they signed out/forgot the device, but the server did not revoke it. This violates the core server-side-revocation promise.

8. MEDIUM — The ephemeral fallback path disables remember-me when _init_session_secret itself fails, but a genuinely unreadable config still crashes startup immediately afterward.

Code evidence:
- web/server.py:92-119 correctly catches failure in _init_session_secret, sets _EPHEMERAL_SECRET=True, and uses a random key.
- The next import-time call, _remember_days() at lines 132-140, catches only TypeError/ValueError. PermissionError, malformed JSON, and other read failures escape.

Exact reproductions:
- Probe test_12 directly exercises the intended fallback: remember_enabled=false, remembered=false, no Expires attribute, no web_sessions row, and a new random key on reinitialization.
  Output: EVIDENCE ephemeral_fail_closed {"persistent_cookie": false, "random_key_changes": true, "remember_enabled": false, "remembered": false}
- Probe test_17 imports the server with config.raw forced to raise PermissionError.
  Output: EVIDENCE unreadable_config_import {"exit": 1, "fallback_reached": true, "subsequent_remember_days_crashes": true}

Assessment:
- Remember-me does not silently enable in the tested fallback. That part is correct.
- The documented “ephemeral session fallback for read-only installs” is not actually available when config reads fail. Startup aborts after reaching the fallback.

Required execution-ordered fix list

1. CRITICAL — Introduce one interprocess-safe, atomic config mutation primitive and use it for every config/auth write.
   - Lock across read + mutate + write, not only os.replace. The lock must cover web process and authtool processes.
   - Make session_epoch monotonic; ordinary config saves must merge the current epoch under the lock and must never write a lower value.
   - Have revoke_all_sessions return an immutable generation/version and do not let delayed work refresh a session to a generation created by a later revoke.
   - Add deterministic tests for test_06 and test_16 interleavings.

2. HIGH — Make auth transitions atomically bump session_epoch and revoke remembered rows.
   - reset, configure_password, and configure_token must advance a monotonic generation even if the new credential text equals an earlier value.
   - Reset + same-token setup and token A→B→A must leave old cookies at 401.
   - Do not rely on salted password hashes accidentally changing av.

3. HIGH — Couple credential verification to the exact auth generation used to issue the session.
   - Under the same synchronization/version protocol, verify against generation N and establish only if the generation is still N.
   - If auth changed, reject/retry; never stamp a login verified under old credentials with the new credential’s av.
   - Add the test_07 interleaving as a regression test.

4. HIGH — Sanitize and validate restored databases before publication.
   - Open the staged restore file, initialize/migrate it, delete every web_sessions row, and recreate only the current caller’s row before os.replace.
   - If any sanitization/recreation step fails, do not publish the DB and return 500.
   - Coordinate restore publication with get_db/request access so no request can observe the restored rows in an intermediate state.
   - Add both cleanup-failure and paused-publication tests based on test_10/test_11.

5. HIGH — Fail closed when session_epoch is unreadable.
   - In SS_TOKEN mode, config read/parse failure must make session_fingerprint return empty or otherwise reject cookie sessions; never substitute epoch 0.
   - Distinguish an explicit stored/default epoch 0 from “epoch unavailable.”
   - Add the test_05 regression.

6. MEDIUM — Make logout revocation truthful and fail closed.
   - Do not return 200 “ok” if the rid row could not be deleted.
   - Preserve enough client state to retry, return 5xx, and present a clear failure; alternatively use a durable revocation mechanism that guarantees the cookie cannot replay.
   - Add a real SQLite DELETE-failure regression based on test_08.

7. MEDIUM — Complete the fallback path and expand tests.
   - _remember_days must handle config read failures consistently with _init_session_secret, choose a disabled value (0), and preserve _EPHEMERAL_SECRET semantics.
   - Test a clean subprocess import with PermissionError and malformed JSON, not just a direct call to _init_session_secret.

Spec/compliance observations beyond the vulnerabilities:
- The implementation substantially covers A-F, but the central guarantees in A2/B2/B3/F are not met because revocation/reset/restore are reversible in the reproduced cases.
- tests/test_web_auth.py case 10 does not cover same-token reset/setup and therefore gives false confidence.
- Its restore test covers “backup before B login,” not the dangerous case “backup contains B, then B is revoked, then backup is restored,” and it does not inject cleanup failure or pause publication.
- Its fallback test invokes _init_session_secret directly and misses the subsequent import-time _remember_days crash.
- The spec’s literal grep requirement (“safescanarr-session-fallback nowhere”) fails because the string occurs in the spec itself. Executable source contains no deterministic fallback constant; this is a verification-script/spec wording defect, not an implementation security defect.
