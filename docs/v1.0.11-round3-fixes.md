Execution-ordered fixes

1. HIGH — Make automatic config changes actual locked read-modify-write operations, including bootstrap.

   Evidence:
   - config.py:120-141 reads the whole config and applies default keys before acquiring save()'s lock.
   - config.py:225-246 locks the final write, clamps only session_epoch, then replaces every supplied field.
   - web/server.py:99-108 similarly reads before locking when generating session_secret.
   - config.py:183,249-256 calls _bootstrap_save() without a lock. _save_held() reads the disk epoch at 234-239 and writes later at 246. There is no exclusive create or recheck of absence under the lock.
   - config.py:198-207 uses a shared config.json.tmp pathname, safe only if every writer actually participates in serialization.

   Reproduction actually run, using only a harmless setting:
   PYTHONDONTWRITEBYTECODE=1 /tmp/safescanarr_venv311/bin/python /home/hermes/.hermes/profiles/skeptic/cache/scratch/check_v1011_round3.py
   DEFAULT_MIGRATION_SETTING {"actual":"nested-ok","errors":[],"expected":"new-setting","joined":true}
   The diagnostic delays an old default-key self-heal save while a locked mutation updates web_ui_url. The stale save then loses the completed update. Identical result on Python 3.14.

   This is not an epoch rollback in that test. The security consequence follows from the same whole-dict write including auth_method/auth_token/auth_password_hash: a completed credential change can be overwritten even though the new epoch is retained. That credential consequence was not dynamically tested. Bootstrap monotonicity is also only a non-atomic check, so the unconditional claim that it cannot lower a concurrently changed epoch is unsupported.

   Fix:
   - Acquire the normal config lock before reading for default migration and session-secret generation; merge only the intended changes into fresh state.
   - Bootstrap under that lock, recheck absence there, and never replace an already-created config with first-run defaults.
   - Keep save() as the locked/clamped low-level snapshot API, but do not mistake its final-write lock for transaction coverage of an earlier read.
   - Add default-migration and secret-generation concurrent-update tests, plus concurrent first-run initialization coverage. Preserve the passing nested-save/exception-unwind behavior.

2. HIGH — Coordinate session deletion, restore publication, and connection lifetime with the same mechanism.

   Evidence:
   - web/server.py:1232 checks the live row, then 1233-1236 recreates the staged row; publication is at 1268.
   - web/server.py:254-261 only locks get_db() when _db is None. Returning an existing Database bypasses _db_lock.
   - database.py:478-482 deletes/commits a remembered row without the restore lock.
   - tests/test_v1011_round2_fixes.py:195-213 pauses delete_web_sessions_except(), before the new live-row check. It does not test the interval after that check.
   - web/server.py:1257-1262 closes the process-wide connection, contradicting 1207-1208's assertion that existing requests retain a usable old-inode handle. A second restore can already have captured that same handle at 1184.

   Reproduction status:
   Original earlier-boundary race was rerun and is fixed. The remaining check-to-publication race and stale-handle failure are statically established synchronization gaps; I did not execute a new post-check auth-replay probe. A passing test that logs out before the check cannot establish publication-time liveness.

   Fix:
   - Define a single publication/revocation ordering and make logout, remembered-row mutations, restore's final recheck, and replacement participate in it.
   - Manage active connection references so replacement cannot close a connection still used by another request. Do not capture the live handle before waiting for publication coordination.
   - Do not merely add another unlocked recheck; there is still a gap after it.
   - Add coverage for deletion after the current recheck, and for concurrent requests retaining a Database reference across restore.

3. HIGH — Give each restore request exclusive ownership of its staging file and sidecars.

   Evidence:
   - web/server.py:1193 uses the fixed db_path + '.restore.tmp'.
   - 1196-1202 opens/truncates/writes it before acquiring _db_lock at 1210.
   - 1240-1248 checks/counts/closes a connection to that path, with publication later at 1268.
   - 1271-1275 cleans the same shared pathname and sidecars after the lock has been released on failure.

   Reproduction status:
   Static concurrency finding; no new overlapping-upload probe was executed. The lock demonstrably does not cover the upload writes by inspection. Therefore it cannot prove that the bytes at the publication pathname are the bytes whose row count was checked. Another restore also owns the same cleanup targets. Possible outcomes include failed restores and corruption; a particular auth bypass was not demonstrated.

   Fix:
   - Allocate a unique private stage per request in the database directory, preserving same-filesystem atomic replacement.
   - Keep staging/WAL/journal cleanup request-owned. Never delete a different request's stage on failure.
   - Serialize final live-connection handoff and replacement; test two ordinary simultaneous restores and one failing restore beside a successful one.

4. HIGH — Finish hostile-schema handling instead of trusting a trigger enumeration plus COUNT.

   Evidence:
   - web/server.py:1211 runs Database(tmp_path) before trigger removal.
   - database.py:98-111 creates/migrates tables, performs UPDATE files, commits, and seeds lifetime state during construction. Uploaded triggers can run before sanitization.
   - web/server.py:1221 constructs DROP TRIGGER from an uploaded name without doubling embedded double quotes. Uploaded names are SQL identifiers, not trusted source text. There is no post-drop assertion that sqlite_master contains zero triggers.
   - database.py:119-128 logs migration failures and continues.
   - web/server.py:1240-1245 checks only web_sessions row count. There is no whole-file integrity validation or required-schema validation.

   Reproduction status:
   The existing simple AFTER DELETE probe is fixed and was executed on both Python versions. No new trigger-identifier payload, writable_schema payload, or corrupt-database exploit was executed. The unsafe identifier construction and initialization-before-sanitization order are directly visible defects; do not turn the absence of a new payload result into a claim that those classes were exhaustively cleared.

   Fix:
   - Prefer importing supported application data into a fresh database built from trusted DDL, discarding uploaded triggers/views/other executable schema and all uploaded web_sessions content.
   - If retaining the staged schema, safely quote arbitrary identifiers, sanitize before application initialization writes, and verify that no uploaded trigger survives. Explicitly reject unsupported schema objects or shapes.
   - Validate integrity and required schema after sanitization; do not treat logged-and-ignored migration errors as a successful restore.
   - Keep the count check, but do not describe it as whole-schema validation or a substitute for staging-file isolation.

Attack-matrix limits

Reentrancy and exception unwind were exercised without a deadlock; this is not an exhaustive fork/signal/reentrant-arbitrary-mutator guarantee. Production mutators inspected here are simple dict updates.

For views, other schema objects, writable_schema and corruption: no new crafted-file bypass is claimed as reproduced. There is no explicit writable_schema enabling in the reviewed restore path. Ordinary SQLite DDL is not a generic trigger-recreation mechanism, and a view referencing web_sessions alone does not establish row resurrection. Nevertheless, initialization-before-sanitization, unsafe identifier interpolation, absent full integrity/schema checks, and shared staging prevent a clean bill for hostile-file handling. Rebuilding one table and counting rows is not evidence that every corrupt or adversarial schema is safe.

Convergence criterion

Do not ship on the assertion 'all five are done.' Keep the passing original-regression tests, but close the stale-config transaction, post-recheck publication, shared-stage, and hostile-identifier/schema-ordering gaps. Then make the documented guarantees match the actual supported lock/read-only boundary and rerun these suites.
