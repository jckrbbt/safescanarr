Round-3 findings 1-6: closure

1. Locked RMW / automatic config changes: NOT CLOSED.
   Bootstrap's disk absence recheck and session-secret merge are implemented. However, default-key migration still computes its missing-key set outside the lock and overwrites a value another writer supplied before acquisition. Bootstrap also returns its losing defaults rather than the winner's config. No deadlock or incomplete counter update was observed in the contention/exception test.

2. Publication/revocation ordering and connection lifetime: NOT CLOSED.
   The exact logout-versus-publication gap is closed in the single-process model: a pause at the actual final os.replace blocks logout; restore and logout both return 200, then the cookie is rejected with 401. But retirement closes a connection on the FIRST retired release, not the last, and production routes leak the new reference accounting. Publication failure can damage the live WAL-backed database. Not all remembered-row deletions participate in the advertised lock.

3. Request-private staging: CLOSED for the reported cross-request interference finding.
   Stage names include process/thread identity and a cryptographic random suffix; final publication is serialized. Both repository simultaneous-restore tests pass, including failed import beside successful restore. Injected import/constraint exceptions leave no stage or upload sidecars. Abrupt process exit leaves a private stage, as expected without crash recovery; this is an operational limitation, not evidence that one request can touch another's stage. See residual notes.

4. Hostile schema handling / required validation: NOT CLOSED.
   Fresh trusted destination DDL, read-only upload connections, parameter binding, physical integrity checks, and dropping uploaded sessions/triggers are implemented. The original trigger regression is dead. However, source schema/row validation is incomplete: a missing files table is silently accepted and published as empty; a source view named state is actually evaluated and imported; a BLOB in a TEXT field is accepted and later breaks an API with non-JSON 500. A known-good current backup does preserve all sampled rows exactly.

5. Actionable error boundaries / repair safety: NOT CLOSED.
   Expected lock failures now produce JSON 500 for both config and revoke APIs and a clean CLI exit 1. Real read-only old configs now serve /login successfully. But fix-lock can unlink a valid lock another repair/writer installed after its failed validation, and imported malformed data still reaches an unhandled non-JSON API 500. Existing valid held locks are not replaced by a solitary fix-lock invocation.

6. Literal release claims: NOT CLOSED.
   README's restore semantics and CHANGELOG's expired-session sign-out qualification were corrected. CHANGELOG still overclaims merged config writes and execution-free uploaded schema. Repair safety/operating restrictions are missing. See issue 6.

Execution-ordered fixes, severity and reproduction

1. HIGH — Make database retirement and publication failure-safe as one lifecycle protocol.

Evidence:
  web/server.py:273-285 increments one global _db_refs for every acquisition.
  web/server.py:295-312 closes ANY db that is not the current _db immediately, without a per-object reference count.
  web/server.py:324-339 sets _db=None but leaves the old count attached to subsequent generations.
  web/server.py:763,769,782,827,887,988,1015,1231,1674,1686,1708,1744 acquire handles without balanced release; there is no teardown handler doing it for them.
  web/server.py:1382-1387 retires the shared DB and unlinks the LIVE database's WAL/SHM/journal BEFORE os.replace succeeds. An exception cannot restore those files.

Reproduction actually executed on both venvs:
  PYTHONDONTWRITEBYTECODE=1 <python> /home/hermes/.hermes/profiles/skeptic/cache/scratch/check_v1011_round4.py

  TWO_RETIRED_HOLDERS:
    Hold two get_db() leases on the same database; perform an ordinary successful restore; release one; query using the other.
    restore=200
    remaining_holder="ProgrammingError: Cannot operate on a closed database."
    current_refs=2

  ROUTE_REFS:
    Four successful GET /api/stats requests increase _db_refs from 2 to 6. Auth's short-lived references balance; the route's reference does not.

  PUBLICATION_FAILURE:
    Put an ordinary state marker into the live WAL with autocheckpoint disabled; inject OSError ONLY for the final os.replace whose destination is Config().DB_FILE.
    restore=500
    A separate sqlite3 connection querying the live marker returns OperationalError('disk I/O error').
    This is observed damage/availability failure, not merely a theoretical rollback concern. I did not claim a measured amount of permanently lost data.

Fix first:
  - Track leases by actual Database object/generation and close exactly when that generation's last lease exits. Never carry a prior generation's counter into the next.
  - Balance all production acquisitions in finally blocks or use an enforced lease/context-manager API. Shutdown waiting must count the retired generation, not unrelated new handles.
  - Design the WAL/connection handoff before deleting sidecars. Keeping old WAL-mode connections open while reusing the same sidecar paths needs explicit treatment, not just a Python refcount. A publication error must preserve a usable live database, including committed WAL data.
  - Add at least two old holders, a new-generation holder, old-holder release after new-generation writes, repeated restores, and final-replace failure tests. The present one-holder test cannot detect first-versus-last release.

Additional synchronization gap, statically established:
  web/server.py:439-444 (_establish_session old remembered-row deletion) and 352-359 (credential-transition hook) execute deletion outside the outer publication lock. Expiration cleanup at 497 also lacks that outer lock, although final rexp checking prevents the obvious expired-cookie case. Logout at 527-532 and API revoke deletion at 716-721 do acquire it correctly.
  The global epoch still protects cookies after credential revocation; I did not demonstrate a new credential-revocation bypass. The old-row removal during re-login does not itself bump epoch and is not covered by the blanket row-deletion coordination claim. Route all security-relevant row retirement through the same generation/publication ordering and test it; do not claim all deletions are already coordinated.

2. HIGH — Validate the source backup contract and imported values before publication.

Evidence:
  web/server.py:1501-1507 silently skips absent tables or zero matching columns.
  web/server.py:1501 uses PRAGMA table_info without checking sqlite_master object type; 1508-1509 SELECTs the object regardless of whether it is a real table or a view.
  web/server.py:1470-1476 validates column names and integrity only on the destination built from the application's own DDL. It cannot establish that the upload was a supported application backup or that its values satisfy application assumptions.
  SQLite's non-STRICT TEXT/INTEGER affinity is not runtime type validation.

Reproduction in check_v1011_round4.py, both interpreters:
  KNOWN_GOOD:
    files=3, errors=1, state=2, lifetime_stats=4;
    restore=200 and exact_rows_equal=true across all four tables.
    Includes Unicode, quoted text, state cursor, and a custom lifetime count.

  EXTRA_TABLE:
    Add an ordinary unrelated table to the same backup.
    restore=200; extra table is not copied. This is correct.

  MISSING_FILES:
    Remove files from an otherwise ordinary known-good backup.
    restore=200; published_file_count=0.
    There is no warning or rejection. Destination schema validation cannot catch the silently missing source data.

  SOURCE_VIEW:
    Replace the source state table with an ordinary constant SELECT view.
    restore=200; its value "from-view" is imported into the fresh destination state table.
    No view object survives, but source view SQL WAS evaluated. Read-only SQLite prevents source writes; it does not prevent executing view expressions. This is not a demonstrated arbitrary-code or cookie-revival exploit.

  BLOB_TEXT_COLUMN:
    Bind ordinary bytes into files.flag_reason in the backup, without triggers or SQL injection.
    restore=200; subsequent GET /api/sheets?state=quarantined returns 500, is_json=false.
    Actual traceback: server.py:808 jsonify -> TypeError: Object of type bytes is not JSON serializable.

Fix:
  - Define supported backup versions and required source tables/columns. Reject missing core tables and unsupported shapes instead of publishing an empty replacement. Optional legacy tables need an explicit compatibility/default policy.
  - Require supported source objects to be ordinary application tables; do not import through views or arbitrary virtual/generated schema without a deliberate safe policy. Discarding destination schema objects is not the same as never evaluating source schema.
  - Validate imported row types, nullability, keys, and app-critical state values before publication. Reject invalid backups without changing live state; do not silently coerce arbitrary BLOBs or fabricate missing state.
  - Keep parameter binding, fresh DDL, both integrity gates, and session-row counting.
  - Make unexpected API internal errors JSON as a defensive boundary, while fixing the import acceptance bug rather than merely hiding it.

3. MEDIUM — Recompute default insertion under the lock; reload a bootstrap winner.

Evidence:
  config.py:130-138 reads before acquisition and captures missing defaults.
  config.py:152-153 applies c.update(missing) to fresh config, overwriting keys that are NO LONGER missing.
  config.py:206-207 returns local bootstrap defaults even when _bootstrap_save saw another writer win and returned without saving at 291-292.

Reproduction, both interpreters:
  STALE_MISSING_DEFAULT:
    Start with remember_me_days absent. Pause the old reader immediately before its mutate() acquires the lock. A normal locked writer sets remember_me_days=91 and completes. Resume the reader.
    expected=91, actual=30, errors=[], joined=true.
    This is a completed benign setting update being lost, not a demonstrated epoch rollback.

  BOOTSTRAP_WINNER (check_v1011_round4_boundaries.py):
    A cooperating writer completes config creation before delayed bootstrap's absence recheck.
    disk_epoch=13, disk_method="token";
    returned_epoch=0, returned_method="".
    Disk overwrite is prevented, but this particular raw() caller sees nonexistent first-run state.

Fix:
  - Apply defaults only where absent in the freshly read locked dict (e.g. setdefault semantics); do not use the pre-lock missing set as unconditional updates.
  - Return/re-read the winning persisted config after losing bootstrap, under appropriate coordination.
  - Add a pause BEFORE lock acquisition. The existing regression pauses save() after the lock is already held and therefore cannot detect this interleaving.

4. MEDIUM — Make fix-lock safe against concurrent repair and active writers.

Evidence:
  web/authtool.py:114-118 validates, catches LockValidationError, and then unconditionally unlinks the pathname after failed acquisition.
  Nothing verifies that the pathname still names the rejected inode. A different repair can install a valid inode and a writer can lock it in that gap; the first repair then unlinks the valid writer's lock and creates a separately lockable file.
  A mode-invalid inode may also still be held by a writer that validated it before the mode changed. Unlink/recreate is not safe maintenance while such writers remain active.

Reproduction, both interpreters, benign controlled scheduling in check_v1011_round4.py:
  FIX_LOCK_VALID_HELD: blocked=true, same_inode=true, exit=0.
    A solitary repair correctly waits for an already-valid held lock and leaves it alone.
  FIX_LOCK_CONCURRENT_REPAIR: valid_winner_replaced=true.
    Pause at unlink after detecting mode 0666. Model a second successful repair and acquire flock on its valid new inode. Resume the original repair while that fd stays held. The original operation removes that valid lock and creates a different inode successfully.
    This uses two cooperating local operations in trusted BASE_DIR, not an untrusted directory attacker.

Fix:
  - Make repair an explicitly exclusive maintenance operation, with service/CLI writers stopped, or introduce repair coordination that all writers honor.
  - Revalidate target identity/state immediately before acting and avoid unlink/recreate of valid or active lock inodes. Identity rechecking alone is not a complete atomic unlink-if-unchanged protocol.
  - Document the required service-user and writer-quiescence conditions, and cover competing repairs. Never weaken ordinary lock validation to make repair appear successful.

5. LOW / operational — State and handle the crash-stage retention policy.

Evidence and reproduction:
  Stage creation at server.py:1333-1344 is request-private and cleanup handles caught Exceptions. A real subprocess terminated with os._exit(79) immediately after staging leaves one .safescanarr.db.restore.<pid>.<thread>.<random>.tmp file.
  Both venvs show ABRUPT_EXIT_STAGE exit=79 with one leftover. Ordinary import/constraint errors show zero leftovers.

This does not reopen finding 3's shared-path race, and killing a process cannot run Python finally blocks. Do not promise crash-proof cleanup. If adding recovery, remove only provably orphaned/aged stages with ownership checks; a generic glob deletion during active requests would reintroduce the original bug. There is no startup orphan cleanup in the reviewed fix layer. A 64-bit random filename suffix plus trusted directory ownership is adequate against the original predictable/shared-path issue here; I found no evidence of cross-request stage interference.

Validation limits and residual risks

  The two physical integrity gates are real. Existing corrupt-upload tests fail closed, and ordinary constraint violations fail before publication. I did not establish a physical integrity_check bypass, test every SQLite corruption shape, or claim that one fetchone() from its result is itself a bypass: the literal 'ok' result denotes success.

  Destination table-column validation does not validate the uploaded schema or app-level data types. Source views being evaluated and missing core tables being accepted are demonstrated, not speculative SQL injection. No new arbitrary-code payload, SQLite-engine exploit, or post-check cookie exploit was constructed.

  _import_table fetchall() at server.py:1509 materializes the whole source table, then executemany imports it. The 512 MiB request cap is not a comparable Python-memory budget; source expressions can also produce values not bounded by file size. No OOM was induced. Streaming batches and explicit row/value budgets are appropriate hardening for this exact import layer, but the release decision does not depend on an invented OOM reproduction.

  File naming is not an exclusive-create primitive (open(...,'wb') at 1338), but trusted BASE_DIR plus random naming removes the original deterministic cross-request collision. No attacker-controlled-directory guarantees are inferred.

  Startup/default self-heal can persist missing defaults before a later user mutator throws. The checked exception contract is that the mutator's own partial edit does not commit and locks unwind, not arbitrary transactional rollback of all nested side effects.

  Initial and final git status/diff numstat match. Repository changes remain the coder's original working tree; neither probe code nor report was written into the repository.

Ship condition

Do not ship based on '80 tests pass.' Fix the database lifecycle/failure protocol, source validation, stale-default merge, and lock repair coordination in that order; preserve the now-working exact logout publication ordering and private staging. Add boundary tests that target the failing schedules rather than the old hooks, make release claims match the supported behavior, then rerun this gate. Finding 3 is closed; findings 1, 2, 4, 5, and 6 are not.
