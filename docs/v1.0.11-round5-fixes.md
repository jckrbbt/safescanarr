Round-4 findings: explicit closure decisions

1. Locked RMW / automatic config changes: NOT CLOSED.
   The stale missing-default overwrite is fixed and the readable bootstrap-winner case now returns the winner. However, the new winner re-read catches read/parse errors and returns losing first-run defaults, including epoch 0. This is a regression in the newly added failure boundary, not evidence of a demonstrated authentication bypass.

2. Publication/revocation ordering and connection lifetime: NOT CLOSED.
   Per-generation counting fixes the first-versus-last retired release. Ordinary stats routes no longer leak, and remembered-row deletions now use the publication lock. But api_quarantine uses its handle after leaving its lease. Other correctly leased writers can finish successfully on an obsolete inode after publication. Checkpoint errors abort only AFTER publication, and SQLite's busy checkpoint result is ignored.

3. Request-private staging: remains CLOSED for the original cross-request shared-stage finding.
   Restore cleanup remains request-private. Startup recovery has separate operational problems below; I did not reproduce two active requests deleting each other's stages in the supported single-web-process model.

4. Hostile schema handling / required validation: NOT CLOSED.
   Missing core tables, direct source views, virtual core tables and the reported BLOB-in-TEXT case are now rejected. Known-good rows round-trip exactly. But validators still accept app-critical state values that subsequently raise unhandled errors in APIs: an ordinary TEXT scan_pid value passes restore and breaks scan/status. The prior requirement included app-critical state validation, not just SQLite storage classes.

5. Actionable error boundaries / repair safety: NOT CLOSED.
   Expected config-lock failures still produce JSON API errors and clean CLI exit 1. Active invalid-inode refusal works. The competing-repair safety claim remains false at the real check-to-unlink boundary, and newly accepted malformed state still reaches a non-JSON API 500. Crash-stage recovery also omits the upload-copy family.

6. Literal release claims: NOT CLOSED.
   Snapshot-save versus merged-mutate wording and maintenance restrictions improved. Remaining absolute claims contradict executed observations: failure-safe publication, safe concurrent repair, never returning nonexistent bootstrap state, and provably-orphaned cleanup.

Fix order within this item:
  - Keep the quarantine lease through its last DB access; audit lexical lease scopes, not just balanced acquisition counts.
  - Quiesce/serialize mutating operations and publication as a protocol. Either drain protected generations before replacing the file, or refuse/defer restore while writers are active. Prevent new writers from slipping into the drain window. Do not wait for lease releases while holding a lock those releases need.
  - Handle shared reads, independent backup connections and scanner-start transitions deliberately. A Python reference count alone does not coordinate SQLite WAL paths or filesystem side effects.
  - Require a successful checkpoint result BEFORE replacement; inspect the returned busy/log/checkpoint fields. Abort before os.replace on error/busy, preserving a usable current generation and its committed data.
  - Do not unlink live sidecar paths while connections able to operate on the old generation remain active.
  - Add the actual quarantine and approval schedules, checkpoint-exception branch and busy-result case to repository regressions. Preserve the currently working exact logout/publication ordering.
