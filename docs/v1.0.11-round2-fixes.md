Concrete issues

1. CRITICAL — session_epoch is still rollbackable through direct config_module.save() paths that bypass config_lock.mutate().

Code evidence:
- config_lock.py:52-63 protects only callers that voluntarily use config_lock.mutate().
- config.py:128-135 auto-fills newly added default keys and calls save(data) directly, with no lock and no epoch monotonic clamp.
- web/server.py:99-107 reads config, sets session_secret, and calls config_module.save(cfg) directly, also outside the lock.
- config.py:181-200 exposes save(cfg) as a raw file replacement helper with no lock and no epoch clamp.

Reproduction evidence from the new probe suite:
- DIRECT_SAVE {"before": 401, "after": 200, "high": 2, "low": 1}
  Steps: log in, keep an old cookie, take a stale cfg.raw() snapshot, call auth.revoke_all_sessions() so the cookie becomes 401, then write the stale snapshot with cfg.save(stale). The old cookie returns to 200 and session_epoch drops from 2 to 1.
- LOAD_MIGRATION_RACE {"before": 401, "after": 200, "high": 2, "low": 1, "thread_alive": false}
  Steps: simulate an older config missing a new default key, pause config._load() at its automatic save(data), revoke sessions while it is paused, then release the stale save. The old cookie is revived.

Why this matters:
- This is not just a malicious unit-test calling private APIs. config._load() really calls save(data) during normal default-key migration, and _init_session_secret() really calls config_module.save() during startup/session-secret creation.
- CHANGELOG.md:13 claims config saves, credential changes, and session revocation are serialized by config.json.lock and session_epoch is monotonic. That claim is false for these code paths.

2. CRITICAL — a crafted backup database can survive restore sanitization and resurrect revoked remembered sessions.

Code evidence:
- web/server.py:1208-1218 opens the staged backup as a normal Database and calls staged.delete_web_sessions_except(None), then recreates the caller row.
- database.py:91-110 initializes/migrates tables but does not inspect or remove hostile schema objects such as triggers.
- database.py:488-497 implements delete_web_sessions_except with a normal DELETE FROM web_sessions, which fires triggers from the restored database.
- web/server.py:1211 does not verify that web_sessions is empty after the delete.

Reproduction evidence:
- MALICIOUS_TRIGGER {"before": 401, "restore": 200, "after": 200, "body": {"status": "ok"}}
  I created a valid backup DB containing a trigger:
  CREATE TRIGGER resurrect_session AFTER DELETE ON web_sessions BEGIN INSERT INTO web_sessions (...) VALUES (OLD...); END
  Then I logged out the remembered session (old cookie was 401), restored the crafted backup, and the old cookie became 200.

Why this matters:
- The restore endpoint accepts arbitrary uploaded SQLite files. SQLite triggers are part of the database schema. Sanitization that only executes DELETE is not sanitization if a trigger can reinsert the deleted row.
- CHANGELOG.md:15 and CHANGELOG.md:21 claim restored backup rows are removed before publication and remembered devices from the old DB cannot get back in. False for this crafted-but-valid SQLite file.

3. HIGH — restore can recreate the caller's remembered row after that same session has logged out during the restore.

Code evidence:
- web/server.py:1201-1202 captures rid/rexp from the request session before sanitization.
- web/server.py:1211-1215 later recreates that rid in the staged DB without rechecking whether the session was revoked in the live DB while restore was in progress.
- web/server.py:1208 holds _db_lock, but ordinary logout/revocation DB methods do not take _db_lock, so logout can run concurrently with the restore staging window.

Reproduction evidence:
- CALLER_RESEED_RACE {"logout": 200, "before": 401, "restore": 200, "after": 200, "thread_alive": false}
  Steps: start restore with a remembered session, pause sanitization before caller-row recreation, use the same cookie to POST /logout successfully, verify the cookie is 401, then let restore complete. The restore publishes a DB that contains the just-logged-out rid again; the old cookie returns to 200.

Why this matters:
- This violates the logout/server-side revocation guarantee. The stale cookie does not need to forge anything; restore re-seeds it from a session snapshot captured before logout.
- This is a natural race between two authenticated requests from the same browser/device, not an artificial mutation of repository code.

4. MEDIUM — config.json.lock is vulnerable to lock-file replacement; the lock is advisory and tied to an inode that an attacker can unlink/recreate.

Code evidence:
- config_lock.py:29 opens config.json.lock with os.O_WRONLY | os.O_CREAT only. It does not use O_NOFOLLOW, does not verify the opened inode against a stable path after flock, and does not protect against unlink/recreate.

Reproduction evidence:
- LOCK_INODE_REPLACEMENT {"first": 3038738, "second": 3038744, "different": true, "first_still_holds": true}
  One thread held an exclusive flock on the original lock-file inode. The lock path was unlinked and recreated; a second _FileLock acquired an exclusive flock on a different inode while the first lock was still held.

Why this matters:
- This requires local filesystem access as the SafeScanarr OS user or equivalent write access to BASE_DIR, so it is not the same severity as remote restore/config bugs.
- But the changelog calls the lock cross-process serialization. That is only true while the lock path is not replaced or symlink-manipulated. At minimum, harden the opener and document the trust boundary.

5. LOW/MEDIUM — the frontend lies on logout failure.

Code evidence:
- web/server.py:576-583 now correctly returns HTTP 500 when server-side remembered-row deletion fails and preserves the session server-side.
- web/static/app.js:56-58 catches every error from /logout and immediately redirects to /login anyway, with no user-visible failure. Because /login redirects authenticated sessions back to /, the user may bounce back in; either way the UI does not report the explicit server failure promised in CHANGELOG.md:17.

This is not the core replay bug anymore — the server-side 500 path exists — but it undermines the user-facing guarantee that sign-out reports failure.

Severity-ranked, execution-ordered fixes

1. CRITICAL — Eliminate unlocked config writes before doing anything else.
   - Make config_module.save() private/unsafe or internally acquire the same lock and apply the session_epoch monotonic clamp.
   - Convert config._load() default-key self-heal and web.server._init_session_secret() to use the locked mutation primitive.
   - Add a regression for the LOAD_MIGRATION_RACE scenario, not just /api/config vs /api/auth/revoke-sessions.
   - If raw save must remain for bootstrap, split it into an explicitly named bootstrap-only helper that cannot write a lower session_epoch over an existing file.

2. CRITICAL — Treat uploaded SQLite backups as hostile schema, not just hostile rows.
   - During restore, drop/recreate web_sessions from trusted application DDL, or at least remove triggers/views/indexes touching web_sessions before deleting rows.
   - Verify after sanitization and before os.replace that SELECT COUNT(*) FROM web_sessions is exactly the intended count, and fail before publication if not.
   - Consider copying only known application tables/data into a fresh trusted SQLite database instead of publishing the uploaded schema wholesale.
   - Add a regression with an AFTER DELETE trigger that reinserts OLD web_sessions rows.

3. HIGH — Make restore caller-row recreation conditional on current revocation state.
   - Do not blindly reinsert rid/rexp captured at request start.
   - Serialize restore with logout/session-row deletion, or re-check the live current-session row immediately before publishing and do not recreate it if it has been revoked.
   - Add a regression where logout succeeds while restore is staged and ensure the old cookie stays 401 after restore completes.

4. MEDIUM — Harden config_lock.py against lock path replacement/symlink attacks.
   - Open with flags that reject symlinks where available (O_NOFOLLOW), validate ownership/mode, and after flock verify that the fd still refers to the current lock path inode.
   - If validation fails, close/retry or abort rather than silently taking a lock on a replaced inode.
   - Document that BASE_DIR must not be writable by untrusted local users.

5. LOW/MEDIUM — Fix the logout UI path.
   - If /logout returns non-2xx, do not redirect as if sign-out succeeded; show the server error and let the user retry.
   - Add a JS/unit or browser test for the 500-preserve logout path.
