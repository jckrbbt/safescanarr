The 114-test Python 3.11 suite passes. The drain protocol nevertheless fails under ordinary controlled scheduling. Its publication flag is LOCAL to api_restore_db(), so new handles are never actually blocked. A timed-out restore also abandons a still-leased generation from subsequent drains. Both retrying restore and overlapping restores can publish while that old writer remains active; its subsequent successful write is absent from the published database. These are executed failures, not hypothetical trusted-directory attacks.

4. fix-lock concurrent-repair safety: CLOSED ONLY BY THE EXPLICIT SUPPORTED-MODE RESTRICTION, not by eliminating TOCTOU.
   CHANGELOG.md:9 now explicitly requires stopped writers and forbids two simultaneous repairs. Within that restricted model I found no new repair blocker. Findings, with severity and execution evidence

1. HIGH — The publication admission gate is a local variable, not shared state.
   Classification: DYNAMICALLY EXECUTED on Python 3.11 and 3.14; source diagnosis also verified.

   web/server.py:277 declares module-level _publishing=False.
   get_db(), lines 336–344, reads that module-level variable.
   api_restore_db(), lines 1484 and 1542, assigns _publishing without any global declaration in the function. Python therefore treats those assignments as local. The module-level flag never becomes True.

   New scratch probe mode: drain_gate.
   Hold a balanced, valid old get_db() lease. Start restore and detect its real Condition.wait() drain. Acquire another handle during that drain; no production method or gate is replaced. The only behavioral adjustment is a short drain timeout.

     DRAIN_GATE global_publishing=false
                new_handle_admitted=true
                same_generation=false
                old_refs=1, new_refs=1
     DRAIN_END restore=500, old_refs=1

   The newly admitted handle is another Database connection to the still-live pathname, not merely an extra reference to the generation being drained. Thus the drain does not exclude new writers, and its checkpoint/publication reasoning is invalid. There is no demonstrated starvation of the exact old counter by these new handles — they use a different generation — but that is worse, not safer: they escape the counter entirely.

   Test blind spot: tests/test_v1011_round5_fixes.py:322–355 starts its supposed 'new writer' at 339–342 BEFORE calling restore at 343. It can acquire and finish before the drain even starts. Its recorded _publishing=False is also exactly what this scoping bug guarantees. The passing test does not test admission during drain.

   Lock/deadlock analysis: Condition.wait() at server.py:1500 releases the underlying RLock, including its recursion state, and release_db() can acquire it and notify. The normal single-restore/last-release case is not deadlocked by holding _db_lock; the repository's quarantine/approve schedules exercise that. Comments at 342–343 and 1480–1483 incorrectly say the drain drops _publishing before waiting. It does not; it should release the lock while KEEPING a working admission gate closed.

   The wait also releases the supposed final-recheck/publication critical section. With the actual broken gate, the shared lock alone does not establish the documented indivisibility of that interval with remembered-row operations. I did not construct a cookie-replay exploit; keep the existing logout ordering regression and add a schedule that includes an active drain, rather than only pausing final os.replace.

2. HIGH — A drain timeout forgets an active generation; retry and a second drain bypass it.
   Classification: DYNAMICALLY EXECUTED on BOTH interpreters.

   web/server.py:379–386 sets _db=None and overwrites the single global _last_retired_key.
   api_restore_db():1492 does that retirement BEFORE waiting.
   Lines 1493–1500 check only _last_retired_key.
   On timeout, lines 1541–1554 do not restore the old shared generation or retain a publication barrier over all active generations associated with the same live file.

   New mode timeout_retry, with a balanced old lease still active:

     first restore=500 (shortened drain timeout)
     second restore=200
     old_refs=1
     old_write="success"
     published_marker=null

   The first 500 itself does not replace the live file, and writes on the old holder still work immediately after it. That narrow outcome is safe. The overall deferred-publication state is NOT safe: the next request creates another shared generation, and the next restore drains only that new generation. The timed-out writer still has the original inode and can successfully write after publication, invisibly to the published file. Adding only 'global _publishing' will not repair this timeout lifecycle: after the timeout the flag is cleared, _db is still None, and the forgotten live-file generation is still leased.

   New mode two_drains, without waiting for any timeout:

     first restore=200, second restore=200
     old_refs=1
     old_write="success"
     published_marker=null

   The first restore is paused in its real drain. The second enters while Condition.wait has released _db_lock, opens/retires a new generation, overwrites _last_retired_key, and publishes. The first then also completes against the overwritten global drain target. Both publish despite the original active lease. The probe uses only two local clients, normal backups, real replacement, and valid paired handle acquisition/release. No raw-handle abandonment or malicious pathname substitution is involved.

   Timeout semantics: the production deadline uses time.time(), not time.monotonic() (1493–1495). A backward wall-clock change can extend the purported bounded wait. This is a STATIC observation, not a separately executed clock failure or independent blocker; use monotonic time while repairing the protocol.

Execution-ordered fixes / final ship condition

1. HIGH: Repair the admission/drain protocol as one change, not a one-word global patch alone. Make publication state truly shared. Serialize publication ownership while releasing the DB mutex for holders to finish; do not let a second drain overwrite a first drain's target. Preserve or account for EVERY still-active generation referencing the live file after a timeout. A failed/deferred restore must leave the next restore unable to bypass that holder. Use a monotonic deadline. Keep the existing checkpoint/error-before-replace gates and post-replace error semantics.

2. HIGH regression coverage, in the same change: start a new acquiring writer only AFTER observing the actual drain; assert it remains blocked. Cover timeout followed by immediate retry with the first holder still leased, two simultaneous restores plus an active holder, release needing _db_lock, and logout during drain. Assert no final replace while any relevant old writer remains, and assert successful writes cannot disappear on obsolete inodes. Keep the actual quarantine/approve release-during-drain cases.

3. MEDIUM: Complete recognized state policy for both poller cursors; validate before publication or reset deliberately, and make consumers defensive. Test restore plus real cursor consumption with benign local responses.

4. LOW: Make pid-list success/unknown a single result; preserve everything on discovery failure. Retain dead-pid-only family cleanup, startup-only placement, and conservative PID-reuse preservation.

5. LOW: Fix stale seam tests and documentation. Assert trace hooks actually fire; distinguish before-comparison replacement detection from the residual unsupported final-unlink window. Keep maintenance exclusivity restrictions rather than promising universal concurrent repair. Remove publication and unknown-liveness claims that the final implementation cannot establish.

Do not ship this round. Bootstrap, scan_pid handling, route lexical lease scope, and isolated checkpoint failure ordering are materially closed. The central publication protocol still permits the same post-publication obsolete-writer failure that round 5 required it to eliminate, and the passing suite does not exercise the failing admission/retry/drain schedules.
